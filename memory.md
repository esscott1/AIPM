# AIPM memory

Decisions made during design (Oct 2026). Newest at the bottom.

- Hub-and-spoke: one PM session, a fleet MCP server, one persistent project team per repo. Agent Teams is not the base (single codebase, experimental).
- Worker agents are called **project teams**. Each can spawn subagents (spike, planner, researcher) scoped to its own repo.
- Teams own commits to feature branches and worktree management (create, merge, rebase), per their own CLAUDE.md and memory.md.
- Opening a pull request requires AIPM's approval. Merging to the default branch requires mine. That branch is whatever git reports (`main`, `master`, or another name). Do not assume the name.
- Cleanup (delete merged feature branches and their worktrees) is the team's job, on a "clean up" command or per its CLAUDE.md after AIPM reports the merge. AIPM is the source of truth for merges; teams never delete unmerged work.
- Budgets are in tokens, not dollars.
- Personal use on my Max plan: teams run through the unmodified `claude` CLI headless; no API key. Switch to API keys if AIPM is ever offered to others. Any API-key use needs my confirmation twice in the PM session (see the 2026-10-24 entries).
- Two interfaces: the PM session (Claude Code) and an AIPM Control Panel artifact in the Claude desktop app (Phase 4).
- Existing repos are adopted with `/adopt-project` (Phase 1). `reconcile` runs before every dispatch so work done outside AIPM (VS Code, Remote Control, merges I do myself) is picked up.
- Repo lives at `C:\src\AIPM`. The initial commit and push were done from WSL Ubuntu at `/mnt/c/src/AIPM`.
- The fleet server runs natively on Windows, the same environment as `C:\src`, VS Code and the Claude desktop app. One session store and one set of paths; teams use the Windows `claude` and `gh` sign-ins and Git Bash. Claude Code sessions for adopted repos never run in WSL, which has its own session store and `/mnt/c` paths.
- `esscott1/AIPM`'s default branch (`main`) is protected on GitHub by the "Protect main" ruleset (GitHub Pro): PR required with 0 approvals, no force push, no deletion, no bypass. All changes, docs included, go through a feature branch and PR. New repos get the same protection on their default branch, whatever it is named. Adoption never applies it; an adopted repo gets it only when I ask.
- In this repo, "clean up" deletes the remote and local branches of merged PRs (procedure in `CLAUDE.md`). GitHub's auto-delete-on-merge stays off so "clean up" is the only trigger.
- Cleanup uses `git branch -d` only, never `-D`, matching my global rules. `-d` refuses squash- and rebase-merged branches, so those are skipped and reported, and I delete them myself. All three GitHub merge methods stay enabled; don't restrict them.
- When I report a merge, Claude confirms it through `gh`, syncs `main` with `origin/main`, then asks before cleaning up (procedure in `CLAUDE.md`).
- `projects.yaml` is local state, not in git: fleet tools write it (adopt, create, pause, resume, retire), so committing it would need a PR for every pause. `projects.example.yaml` documents the format. Each field has one home: the registry in `projects.yaml`, `session_id` and `last_seen_commit` in `fleet/sessions.json`. Accepted downside: lose the machine, re-adopt each repo.
- The registry allows only `plan` and `acceptEdits` permission modes and rejects `bypassPermissions`. The `claude` CLI also offers `auto`, `manual` and `dontAsk`; add one deliberately if a team needs it.
- A repo path is checked for `.git` when it is added, not when the registry loads, so one moved repo doesn't stop the fleet server from starting.
- Gotcha: `bash` on PATH is WSL (`C:\WINDOWS\system32\bash.exe`). Git Bash is at `C:\cmdr\vendor\git-for-windows\bin\bash.exe` (git comes from cmder). `fleet.doctor` checks this.
- Gotcha: uv fails TLS to PyPI on this machine ("invalid peer certificate: UnknownIssuer"). Set `UV_SYSTEM_CERTS=1` or pass `--system-certs`.
- Gotcha: `claude --help` (2.1.289) doesn't list `--max-turns`, but the CLI accepts it (an unknown flag after it is the only one reported). The fleet server passes it only when a project sets `max_turns`.
- The fleet server uses the `mcp` Python SDK 2.x. In 2.x, `FastMCP` is `MCPServer` (`mcp.server.mcpserver`). A tool must raise `ToolError` for a message the PM should see; any other exception reaches the PM only as "Error executing tool <name>". Tests use `Client(server)` in-process and `Client(StdioServerParameters(...))` for a real subprocess.
- `.mcp.json` launches the server with `uv run --quiet --directory C:/src/AIPM python -m fleet.server` and sets `UV_SYSTEM_CERTS=1`. The server re-reads `projects.yaml` and `sessions.json` on every call, because other tools write them. `AIPM_REGISTRY` and `AIPM_SESSIONS` point it at other files for tests.
- A headless `claude -p` call that just replies "ok" reports about 50k tokens, mostly cached system prompt and tools. Every team dispatch starts from that baseline; size `max_tokens_per_job` with it in mind.
- Gotcha: from Windows, git refuses `C:\src\AIPM` with "dubious ownership" because the folder is owned by `BUILTIN\Administrators` (created from WSL). Workaround: `git -c safe.directory=C:/src/AIPM ...`, or add it once with `git config --global --add safe.directory C:/src/AIPM`.
- Teams run on my claude.ai sign-in, never an API key. If `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` is set, `claude` bills that API account instead, so the fleet server drops both names from each team's environment without reading them. Using an API key for a team needs me to confirm twice in the PM session: AIPM asks and explains the billing change, then asks again before the first dispatch. `fleet.doctor` checks that `claude auth status` reports `claude.ai`. My Max plan has no automatic usage increase, which is how my spending is capped.
- I'd rather max out my plan than have a team fail on an AIPM limit. The per-job token cap defaults to 100K and is report-only: `get_report` flags `over_token_cap`, and the job keeps running. `--output-format json` reports usage only at the end of a run, so stopping mid-run would need `stream-json`. The headless baseline alone is about 50k tokens (mostly cache reads), so most real tasks will go over 100K. Revisit whether the cap should stop jobs once I understand token counts better. The plan's usage limit is the hard stop; the job fails with claude's message and the session is kept.
- `dispatch` runs jobs in the background: it returns a running job, and the PM polls `get_report`. One job per project at a time. Job records are `fleet/jobs/<id>.json`, refreshed every 30 s while running; a running record older than 2 minutes is reported `lost`. If the fleet server dies, the `claude` child keeps running and may finish unrecorded.
- The AIPM brief (feature branch, no PR, structured report) is appended to every task prompt, not passed with `--append-system-prompt`: that text is recorded on a session's first request and replayed unchanged on every resume.
- The report is enforced with `--json-schema` (summary, branch, changed, tests, blockers, next_step). The runner reads `structured_output` and falls back to parsing `result` as JSON. Unverified against the real CLI until the live check.
- Team processes get `stdin=DEVNULL`: the fleet server speaks MCP on its own stdin, and a child that inherited it could read the MCP stream.
- Gotcha (expected, unverified): headless `acceptEdits` auto-approves file edits only. Bash commands such as tests or `git commit` are denied unless the repo's settings allow them, so a team may report them as blockers. Check in the live check.
- Gotcha: on Windows, `os.replace` fails with PermissionError while another thread has the target open for reading. `fleet/files.py` retries the replace briefly.
- Live check of `dispatch` (real `claude -p` runs) is deferred until later in Phase 1, before the exit test. Ask me first.
- Adopting a repo only registers it: `/adopt-project` writes `projects.yaml` and `sessions.json` and changes nothing in the repo (no files, branches, commits or GitHub settings). Every change to an adopted repo comes from a task dispatched to its team, including adding `memory.md`, subagents or the "Protect main" ruleset. No AIPM section in team CLAUDE.md files; the dispatch brief carries AIPM's rules. (2026-10-25)
- Every new team, adopted or created, starts in a fresh session: a fresh set of eyes, not biased by earlier sessions. Its first task begins by reading the `context_docs` I picked at adoption (CLAUDE.md, memory.md, architecture, roadmap and other plans). AIPM ignores existing sessions in the repo's folder: it never lists, resumes or deletes them. Considered and dropped: importing or taking over an existing session at adoption. (2026-10-25)
- A dispatch to a paused project runs nothing: AIPM reminds me the project is paused and saves the task to `fleet/queue.json`. `resume` lists queued tasks for me to dispatch or discard; they never run on their own. (2026-10-25)
- `last_seen_commit` is written at adoption (and when `create_project` registers a new repo): the default branch's current commit, with no session. `reconcile` diffs since that commit; it does not create the field. (2026-10-25)
- The fleet server is Python 3.12+. Teams run through the unmodified `claude` CLI (`claude -p`), not the Claude Agent SDK library. (2026-10-25)
- The protected branch is the repo's default branch, whatever git names it (`main`, `master`, or another name). Do not assume `main`. On this repo the ruleset is still named "Protect main" because that is this repo's default branch. (2026-10-25)
- job-search-assistant is its own repo at `C:\src\job-search-assistant` (`esscott1/job-search-assistant`). It is not inside `esscott1/ClaudeCowork`. (2026-10-25)
- If a file a running team is changing is also changed outside that job, the team reports that file to the PM, pauses, and waits for direction. It does not keep editing the file, and it does not stop the whole job on its own. The usual direction is to continue after a human has checked the outside change. This is Phase 2; it is not built yet. (2026-10-25)
