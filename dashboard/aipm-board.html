    Project teams

    Three teams, each scoped to one repo

    Every team is a lead session that keeps context in its repo and spawns subagents for spikes, planning and research. Subagents inherit the team's folder and permissions, never another repo's. Each team commits to its feature branches and creates, merges and rebases its own worktrees according to its CLAUDE.md and memory.md. When AIPM reports a merge, the team deletes the merged branch and its worktree, on a clean-up command or by its own CLAUDE.md rule.

    New-project bootstrap

    One ask becomes a source-controlled repo with a working team

    1. Propose

      PM drafts name, visibility, goal and template. Your approval

    2. Scaffold

      C:\src\<name> with README, .gitignore, CLAUDE.md, .claude/agents/

    3. Init

      git init -b main and first commit

    4. Publish

      gh repo create esscott1/<name> --private --source . --remote origin --push

    5. Register

      Append the entry to projects.yaml

    6. Staff

      Start the team session, save its ID, hand it a kickoff task

    Needs the gh CLI installed and signed in on your machine. The fleet server never stores a GitHub token.

    What the PM can call

    list_projectsRegistry entries and last activity
    adopt / retire / pause / resumeBring a repo under AIPM, release it, or hold it while you work directly
    reconcile(project)Catch up on work done outside AIPM before the next dispatch
    dispatch(project, instruction, mode)Run a task in one team; returns a job ID
    broadcast(instruction, projects)Same ask across several teams in parallel
    request_pr / approve_pr / reject_prTeam asks to open a PR; the PM approves or sends it back
    notify_merged(project, pr)Tells a team its PR merged so it can clean up
    job_status / get_report / cancelTrack and collect background work
    create_project(name, visibility, template)The bootstrap flow above
    standup()git log, open PRs, last report and tokens used per repo
    Sessions are stored per folder, so the fleet server always resumes a team from its registered repo path. Moving a repo means re-registering it.
